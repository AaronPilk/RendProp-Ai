## Summary
The function code is generally careful (RLS-scoped reads, service-role writes behind membership checks,
atomic RPCs for render creation/publish/metering, staged-copy upload verification, durable rate limits,
SSRF guard on the fal proxy). The serious problems are **contract and lifecycle gaps, not crypto**:
(1) the repo is missing **four migrations that exist in production** (`plan_entitlements`,
`effective_plan()`, `plan_render_cap()`, `orgs.trial_ends_at`, the COGS ceiling in `log_job_cost()`,
the trial-on-signup trigger) — a database built from the repo cannot run the deployed functions, and the
committed `create_render_job` enforces 20/100/400 renders while the site sells 8/25/80;
(2) any on-device render ≤ 64 MB **cannot be published** — the iOS single-PUT sends
`Content-Type: video/quicktime` while the `role:"render"` ticket declares `video/mp4`, and `/complete`
rejects the mismatch and deletes the object; (3) **leads are captured but never delivered to the agent**
(no read endpoint, no notification, a single Rendprop-owned GHL location); (4) every app publish burns a
plan "AI render" the pricing page says is free, on a calendar-month counter, and the live orgs sit on
`free` = 1 render/month, so a tester can publish one tour a month; (5) failed publishes leave `created`
jobs that lock the workspace after three; (6) the public agent card falls back to the org name, which the
signup trigger sets to the user's **email**; (7) deleting/selling/archiving a listing never takes its
public tour down, and app-published tours never get a poster. What is solid: the upload TOCTOU fix,
multipart bounds, `publish_render` deriving `staged` server-side, deletion tombstoning order, beacon clamps.

## Findings (most severe first)

### F-supabase-01 · P0 · On-device renders ≤ 64 MB can never be published (content-type mismatch deletes the upload)
- Where: `services/supabase/functions/uploads/index.ts:474-475` (declared type defaults to `video/mp4` for `role:"render"`), `:382-385` (`typeOk` requires `observedType === declaredType`), `:386-397` (mismatch → object deleted, 400); iOS `apps/ios/Rendprop/Upload/DirectUploader.swift:24-29` (`putRequest` hardcodes `Content-Type: video/quicktime`), `Upload/UploadManager.swift:431` (single mode uses `putRequest`), `Networking/LiveAPIClient.swift:118-131` (`requestUpload` never sends `content_type`).
- What's wrong: The server picks the declared type when the client omits it: `video/quicktime` for captures, **`video/mp4` for role=render**. The app's single-PUT path (used whenever `bytes ≤ 64 MB`, i.e. every short or lower-res scrub master) always PUTs with `video/quicktime`. `/complete` HEADs the staged object, sees `video/quicktime ≠ video/mp4`, **deletes the staged object** and returns 400 `Uploaded object content-type "video/quicktime" is not an allowed video type`. Multipart (> 64 MB) is unaffected because R2 takes the type from `CreateMultipartUpload`. The AUDIT-RESPONSE even records that the iOS uploader hardcodes `video/quicktime` (§P0-2) — round 2 then added the equality check that breaks it.
- User-facing effect: "Publish" on any tour whose rendered mp4 is under 64 MB fails with a bare "Server returned status 400." (see F-14), the bytes already uploaded are thrown away, and retrying repeats it forever. Photos are fine (iOS mirrors the declared type).
- Fix: iOS — pass `content_type` in `requestUpload` (derive from the file: `.mp4` → `video/mp4`, `.mov` → `video/quicktime`) and use that same value in `DirectUploader.putRequest(url:contentType:)`. Server — in `uploads/index.ts` keep the allowlist check but only enforce `observedType === declaredType` when the client actually declared one (track `declared_by_client` or accept any allowlisted type when the ticket's type was defaulted); keep deleting on allowlist failure. Add a regression test that PUTs a small mp4 with `video/quicktime` against a render ticket.

### F-supabase-04 · P1 · Every app publish consumes an "AI tour render" from the plan; counter is calendar-month; live orgs are on `free` (1/month)

### F-supabase-05 · P1 · Failed `publish-app` leaves `created` jobs that lock the workspace after three; no cancel endpoint; iOS idempotency keys are random
- Where: `renders/index.ts:104-123` (create then publish, no cleanup on publish failure); live `create_render_job` in-flight check (`0008_audit_round4.sql:129-134`: `status in ('created','queued','claimed','processing') >= 3 → RP429`); no `DELETE /renders/:id`; iOS `LiveAPIClient.swift:52-54` (`Idempotency-Key = UUID()` freshly minted per request, so a retry never replays); `services/worker/settings.py:121` (`claim_statuses = ("created","queued")`).
- What's wrong: If `publish_render` raises after `create_render_job` succeeded (asset not `bucket='renders'` → RP400; no `duration_s` on a ticket without probed metadata → RP400; a chapter `t_ms`/`sort` cast error), the job stays `created` forever — nothing will ever advance it (no worker for app jobs) and it still counts against both the in-flight limit and the monthly cap. Three such attempts → `RP429 … 3 renders in flight — wait for one to finish`, permanently. The idempotency replay that would return the same job needs the *same* key, but the app mints a new UUID per request. Separately, if the Python worker is ever running, it polls `created` jobs and can claim an app job in the milliseconds between the two RPCs and start re-rendering the scrub master.
- User-facing effect: After a few failed publishes the app can never publish again for that workspace (402/429 with no recovery path).
- Fix: In `publish-app`, wrap the pair: on `publish_render` failure, `update render_jobs set status='failed', error=…` for the just-created job (service-role, or a new `fail_render_job(p_job)` RPC gated by role), so it drops out of the in-flight count. Exclude `failed`/`canceled` from `v_used` or keep counting only `ready` jobs. Add `POST /renders/:id/cancel`. Have `create_render_job` accept `p_source='app'` and set status `'publishing'` (a status the worker does not claim). iOS: derive the key deterministically (`sha256(listingId+assetId)` or persist it with the upload state) so retries replay.
