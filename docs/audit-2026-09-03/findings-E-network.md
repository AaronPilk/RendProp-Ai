# Findings — E · Networking / Upload / Auth / Config (iOS ↔ Supabase Edge Functions contract)

## Summary
The wire plumbing is mostly clean: snake_case DTOs, tolerant decoding, path-segment URL building, Keychain-backed tokens, single-flight refresh, a genuinely resumable multipart engine with bounded temp disk. But three things break the product end-to-end in the shipping configuration (`useLiveBackend = true`, `enableAuth = true`): (1) every app-published tour whose rendered mp4 is ≤ 64 MB (roughly any walkthrough under ~75 s) is **rejected at `/uploads/:id/complete`** because the app PUTs with `Content-Type: video/quicktime` while the server declared `video/mp4` for `role:"render"` — the object is deleted and the publish fails forever, with no message; (2) the entitlement layer every AI route depends on (`plan_entitlements`, `effective_plan`, `plan_render_cap`, the `solo` plan) **does not exist in any migration in the repo**, so `entitlementFor()` falls back to the trial allowance (aerials 0 → every Aerial Intro is a 402; Topaz 0 → every Cinematic/4K tier silently downgrades; reels 1/month; photo edits 10/month) and `create_render_job` still hardcodes 20/100/400 against a pricing page that sells 8/25/80 — the "enforced = published" hard rule is violated on every axis; (3) the client throws away the server's `{error}` envelope, so users see "Server returned status 402." instead of the upgrade/quota/duplicate message the server wrote for them. Beyond that: a publish that fails (or an upload that resumes after relaunch) has no way to ever be published; `updateListing`, `beginPhotoBatch`, `signInWithApple()`, `createRender`/`renderStatus` are dead code in live mode, so sold/Zillow/photo/headshot edits never reach the hosted page; `Idempotency-Key` is a fresh UUID per request so retries double-create jobs and double-bill; and the sign-in email leaks as the public agent name until the card is set. Solid: URL building, DTO key mapping, Keychain migration, refresh rotation, multipart part math/ETag manifest, stale-task filtering, no PII logging, no ATS exceptions, anon key is a real `role:anon` key.

## Findings (most severe first)

### F-E-01 · P0 · Every app-published tour ≤ 64 MB is rejected at `/complete` (content-type mismatch) — short walkthroughs can never get a share link
- Where: `apps/ios/Rendprop/Upload/DirectUploader.swift:24–29` (`putRequest` hardcodes `Content-Type: video/quicktime`); `Networking/LiveAPIClient.swift:118–131` (`requestUpload` never sends `content_type`); `services/supabase/functions/uploads/index.ts:474–475` (render default `video/mp4`), `:382–397` (`typeOk` requires `observedType === declaredType`, then **deletes the object** and 400s); `Render/RenderEngine.swift:63–64,133–134,343` (output is `.mp4`, 720p/60 fps H.264 @ 14 Mbps ≈ 1.75 MB/s).
- What's wrong: `POST /uploads {role:"render"}` stores `content_type = "video/mp4"`. For files ≤ 64 MB the server returns `mode:"single"`; `UploadManager.launchSingle` PUTs with `DirectUploader.putRequest` → header `video/quicktime`; R2 stores that as the object's type. `/complete` HEADs the staging object: `observedType = "video/quicktime"`, `declaredType = "video/mp4"` → `typeOk = false` → `deleteObject` + `update {uploaded:false}` + `400 "…content-type "video/quicktime" is not an allowed video type"` (message itself is wrong — the type is allowed; it merely differs from the declaration). At 14 Mbps, 64 MB ≈ 36 s of rendered tour ≈ 73 s of walkthrough at the 2× speed factor — i.e. most apartments, restaurants, retail floors, and every "quick" capture. Multipart (> 64 MB) is unaffected because `createMultipartUpload` sets the type server-side.
- User-facing effect: "Publishing tour…" → `UploadManager.handleSingleCompletion` catches → `.failed` → `onUploadFailed` → `UploadError.failed` → RenderStatusView shows "Saved on your phone — we couldn't publish the share link." Settings "Resume upload" mints a NEW ticket (`reconcileAndResume` L333 → `requestTicketAndStart`) and re-uploads → same 400 → loop, and each attempt leaves an orphan `capture_assets` row and burns the org's daily ticket budget. The same bug hits the Cinematic/4K path (`enhanceThenPublish` uploads the master first) so the AI enhance always "falls back".
- Fix: (a) iOS — add `contentType` to `requestUpload` (derive from the file extension: `mp4→video/mp4`, `mov→video/quicktime`, `m4v→video/x-m4v`) and send it as `content_type`; persist it on `UploadManager.State` as a new **Optional** field (`var contentType: String? = nil`, decoded with `decodeIfPresent`); change `DirectUploader.putRequest(url:)` to `putRequest(url:contentType:)` and pass the persisted value; default the render role to `video/mp4`. (b) Server — soften `typeOk` to "observed ∈ allowlist" for `kind === "video"` (the declared/observed equality only matters for photos where the type is user-visible), and fix the error message to say "does not match the declared type". (c) Treat a `/complete` 400 as **terminal** on the client (do not re-ticket in a loop) and surface the server message (see F-E-04).

### F-E-02 · P0 · The entitlement layer the AI routes depend on does not exist in the repo → aerials/Topaz always 402, reels 1/month, photo edits 10/month; render caps ≠ published caps
- Where: `services/supabase/functions/_shared/entitlements.ts:55–73` (RPC `effective_plan` + table `plan_entitlements`, "migration 0010"); `migrations/` contains only `0001…0008` — no `plan_entitlements`, `effective_plan`, `plan_render_cap`, nor a `solo` plan (grep across the repo: only the three `.ts` comments mention 0010); `tests/invariants.sql:82–94` asserts `plan_render_cap('solo')=2 … orgs_plan_check like '%solo%'` — neither exists; `migrations/0001_init.sql:25` (`plan in ('free','pro','team')`); `migrations/0008_audit_round4.sql:136–143` (`create_render_job` cap `case v_plan when 'team' then 400 when 'pro' then 100 else 20`); `services/edge/tour-host/public/pricing.html:104–150` (Solo 8 renders/150 edits/8 clips/2 aerials; Pro 25/300/20/6; Team 80/600/40/15 + 2 drone; trial 1/10/1).
- What's wrong: `entitlementFor()` catches the RPC error and returns `TRIAL_FALLBACK` (`aerials_per_month: 0`, `topaz_per_month: 0`, `reels_per_month: 1`, `photo_edits_per_month: 10`, `cogs_ceiling_cents: 200`) for **every org, forever**. `guardGenerate("aerial")` → `monthlyCap <= 0` → `quotaError` → **402** on every `POST /ai-video/aerial`; same for `drone`. Meanwhile render creation uses a different, hardcoded table (20/100/400 by `free/pro/team`) that matches neither the pricing page nor the test. The hard rule "Enforced entitlements must equal published entitlements" is violated on renders, photo edits, clips, aerials and Topaz simultaneously; the `solo` plan the site sells cannot even be stored (`orgs.plan` check).

- Fix: add the missing migrations to the repo (they must be the source of truth): `0009_plans.sql` — `orgs.plan check in ('trial','free','solo','pro','team')` + `plan_render_cap(text)` + `effective_plan(p_org)` (trial expiry → `free`); `0010_entitlements.sql` — `plan_entitlements(plan pk, renders_per_month, photo_edits_per_month, reels_per_month, aerials_per_month, topaz_per_month, seats, cogs_ceiling_cents, price_cents)` seeded with the pricing-page numbers (trial 1/10/1/0/0, solo 8/150/8/2/0, pro 25/300/20/6/0, team 80/600/40/15/2). Rewrite `create_render_job` to read `plan_entitlements.renders_per_month` via `effective_plan()` instead of the `case` literal. Keep `TRIAL_FALLBACK` but make the fallback path **log loudly and return 503**, not silently 402 — a missing table must not masquerade as a plan boundary. Verify `tests/invariants.sql` passes against a fresh `supabase db reset`.

### F-E-03 · P1 · A failed or interrupted publish can never be published later — no re-publish path; resumed uploads complete but nothing publishes
- Where: `Screens/RenderStatusView.swift:96` (copy: "…You can view it now and share it later."), `:387–396` (`performPublish` catch → `publishFailed`); `RendpropApp.swift:135–179` (`publishTour` — the only publisher, called only from RenderStatusView:377); `Screens/FlythroughDetailView.swift:185–203` ("Publish to get your share link" card with **no action**); `Upload/UploadManager.swift:139–168` (`init` auto-`resume()`s a persisted `.uploading` state), `:692–710` (`markDone` → `onUploadComplete?` is nil after relaunch), `:228–251` (`upload()` continuation lives only in the RenderStatusView task).
- What's wrong: the publish sequence (ensure listing → upload role=render → publish-app) exists only inside the RenderStatusView task. If publish fails (F-E-01, network, 402, sign-in "Not now"), the listing has a local tour but no slug and the only way to re-run `publishTour` is to go back through Review & Submit and **re-render the whole video**. If the app is killed/backgrounded during the upload, `UploadManager` resumes the background transfer on relaunch, `/complete`s it, sets `.done`, Settings shows "Complete · 100%" — but `publish-app` is never called; the uploaded render asset is orphaned in R2 and the listing never gets a link.
- User-facing effect: the detail page says "Publish to get your share link — Create your tour and it becomes a live page" while there is no publish button; the user's only recourse is a full re-render (minutes) and a full re-upload.
- Fix: persist a `pendingPublish` record (listing local id, output rel path, durationS, speedFactor, tier, enhancements) in `AppModel` (new Optional Codable field on the persisted state) when `publishTour` starts, clear it on success; on app launch and when `UploadManager.didCompleteNotification` fires with a matching `listingID` (the notification already carries it, L704–710), call `publishApp` with the completed `assetID`; add a "Publish tour" button to the FlythroughDetailView pre-publish card that calls `publishTour` with the existing `model.tours[listing.id]` output (no re-render) and shows `uploads.state.fractionComplete`. `UploadManager.State` should also carry `listingLocalID: UUID?` (Optional) so a resumed role=render upload can be matched back to its listing.

### F-E-04 · P1 · The server's `{error}` message is discarded — 402 (upgrade), 429 (wait), 409 (duplicate / already complete / account deleting), 413 (image too big) all surface as "Server returned status N."
- Where: `Networking/LiveAPIClient.swift:62–68` (`execute`), `Networking/APIClient.swift:229–239` (`APIError.badResponse(Int)` carries only the code); server envelope `_shared/http.ts:40–47`, `_shared/entitlements.ts:76–88` (human-readable 402/429 text written specifically "so the app can prompt an upgrade, not just fail"), `renders/index.ts:28–33`, `uploads/index.ts:132,140,324,367,394–395,429`, `ai-video/index.ts:117,121,306`, `ai-photo/index.ts:64,68,181`.
- What's wrong: no code path parses the JSON body of a non-2xx response; there is no `case quota`/`case unauthorized` in `APIError`; nothing distinguishes a plan boundary (402) from a rate limit (429) from a duplicate (409).
