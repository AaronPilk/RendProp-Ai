# Findings — H · tour-host Worker, hosted player, portfolio, marketing site, legal, demo

## Summary
The Worker itself is well-built: escaping is applied on every user-supplied string I could find, URL schemes are allow-listed, the CSP is tight, HEAD/cache/404/502 paths are correct, the hls.js SRI hash matches cdnjs byte-for-byte, JSON-LD parses, every internal link/anchor/asset on the four marketing pages resolves, and the live `plan_entitlements` table matches the numbers on /pricing and /llms.txt. The problems are almost all *product-truth* problems: the site, /llms.txt and the FAQ describe a hosted "single-property website" (story, gallery, reel, floor plan, features), a portfolio page at `/a/<handle>`, "your face on every tour", leads "delivered to you", and per-tier 4K/priority/seats — and for a real (non-demo) tour **none of that exists**: the app never collects or uploads any of the microsite data, nothing in the entire stack ever writes `orgs.handle` (so every portfolio URL 404s), the headshot is never uploaded, leads are stored but never shown to or sent to the agent, and the tier differences are not enforced. Two live defects on top: the only real published tour on the production DB points at an R2 URL that returns 404 (buyers get a black page, and the player has no failure state), and the hosted scrub engine lacks the jank-watchdog fix the iOS copy already has, so the in-app hosted demo card can silently degrade to an autoplay loop. Also: when an agent has not filled in the card, the public page prints the account's sign-in email as the agent's name (confirmed on live data: 2 orgs, both named by email, 1 without a brand name).

## Findings (most severe first)

### F-H-01 · P0 · The only real published tour on prod serves a dead video (public R2 URL → 404), and the player has no failure state
- Where: `services/supabase/functions/tours/index.ts:109-111,134` (builds `scrub_url` from `R2_PUBLIC_BASE_URL + video_key`); `services/edge/tour-host/src/player.ts:623-636` (error path), `:474` (12 s unconditional `begin()`), `:387-392` (`sizeTrack` never called before `loadedmetadata`), `:430-432` (no `Math.max(1, …)` guard).
- What's wrong: Live check (read-only): `renders` has exactly one published row (slug `WAiQXhEq3o`, published 2026-08-21, `video_key = renders/<org>/<listing>/<asset>.mp4`, `capture_assets.uploaded = true`, 48.5 MB, `bucket = renders`, `stream_uid = null`, `poster_key = null`). `GET https://pub-70303ef2….r2.dev/renders/…/…mp4` returns **404** (HEAD and GET). So `GET /tours/WAiQXhEq3o` returns a `scrub_url` that does not resolve, `hls_url: null`, `poster: null`. In the page: `directSrc()` fires `error` → `CFG.hlsUrl` is empty → nothing happens; after 12 s `begin()` runs anyway, the loader fades, `reportViewAndDelivery()` counts a view + `streamed_minutes = 27.68/60`, and `tick()` runs with `total = track.offsetHeight - innerHeight = 0` (track was never sized because `sizeTrack()` only runs on `loadedmetadata`/`resize`) → `p = NaN`, `scaleX(NaN)`. Nothing is thrown; the viewer sees a black stage, "RENDPROP", the listing chip, and a bobbing "Scroll to fly through" hint forever. Root cause of the 404 is outside this slice (either the r2.dev public domain is bound to `rendprop-public` while app publishes land in `rendprop-renders`, or the object was removed/never promoted) — but the web page must not present a dead tour as a live one.
- User-facing effect: every recipient of the one real share link that exists today gets a black page. Any future tour whose object is missing/expired gets the same, with a *view* recorded and streamed minutes credited.
- Fix: (1) Backend/iOS reviewers: confirm which bucket `pub-70303ef2…r2.dev` is bound to and where `role:"render"` uploads land; add a post-publish HEAD of `scrub_url` to `publish-app` (fail the publish, or mark the render `unavailable`) so a dead link can never be handed to the app. (2) Player: on `video.error` with no HLS fallback (and on the 12 s timeout with `readyState === 0`), replace the loader with an explicit "This tour's video isn't available right now" state, do **not** call `begin()`/`reportViewAndDelivery()`, and hide the scroll hint. (3) Call `sizeTrack()` once at setup when `CFG.durationS > 0`, and port the iOS guards: `const total = Math.max(1, …)` and `video.readyState > 0` before assigning `currentTime` (see F-H-07). (4) Have the Worker HEAD `scrub_url` when rendering (cheap, cached 60 s) and render the unavailable state server-side if it 404s.

### F-H-06 · P1 · Lead form: `novalidate` + generic error handling turns every user input mistake into "Could not send right now", and lets an empty/phone-less request through
- Where: `src/player.ts:229` (`<form id="leadform" novalidate>`), `:218-222` (`required` on name/phone), `:562-572` (`if (!res.ok) throw new Error('bad')` — the server's JSON message is discarded; `alert('Could not send right now. Please try again.')`); server `leads/index.ts:111-126` (400s: "name, phone, or email is required", "email is not valid", "phone is not valid" `/^[+()\d\s.-]{7,40}$/`).
- What's wrong: `novalidate` disables the browser's `required`/`type=email` checks, and there is no JS validation, so (a) submitting the form empty or with "call me" as the phone yields a 400 that the page reports as a transient outage, (b) a name-only submit is accepted server-side even though the RE copy says "the agent will text you times", and (c) with Turnstile enabled the same consumed token is re-sent on retry (no `turnstile.reset()`), so the retry fails with 403 → same misleading alert.
- User-facing effect: Buyers with a typo are told to "try again" with no hint; agents receive leads without a phone number.
- Fix: Drop `novalidate` (or keep it and validate in JS): require name + phone for the lead form, mirror the server regexes client-side, show an inline field error; on `!res.ok` read `res.json().error` and display it (400 → inline, 429 → "too many requests", 403 → "please complete the check"); call `window.turnstile?.reset()` on any failure; replace `alert()` with an inline message; add real `<label>`s (placeholders are the only labels today — a11y).

### F-H-07 · P1 · Hosted scrub engine is behind the iOS copy: naive jank watchdog can drop the in-app hosted demo card (and janky phones) into an autoplay loop for good; missing NaN/readyState guards; rail jump not clamped
- Where: `src/player.ts:427-440` vs `apps/ios/Rendprop/Resources/player/index.html:336-360`; `RendpropApp.swift:466-468` loads `https://rendprop.com/f/estate-demo?embed=1` into a 460 pt `WKWebView` inside a `ScrollView`.
- What's wrong: The hosted `tick()` still uses `if (now - lastTick > 90){ if (++longFrames > 24) return fallbackLoop(); }` — 25 slow frames *ever* (never decremented, suspensions counted) permanently abandons scrubbing and switches to `video.loop = true; video.play()`. The iOS file fixed exactly this on 2026-08-26 ("gaps over ~1 s are suspensions … smooth frames pay the counter back down — so an embedded 460pt player can't drift into autoplay over a long session") — but the embedded 460 pt player on the Home screen is now the **hosted** page, which lacks the fix. WebKit throttles rAF for an offscreen webview to ~10 fps (100 ms gaps < 1000 ms) → 25 frames ≈ 2.5 s offscreen → fallback. The iOS copy also guards `Math.max(1, total)`, `video.readyState > 0`, and clamps `c.t / duration` on rail taps (`:304-307`); the hosted copy does none of these (`:401` scrolls past the track into the microsite for a chapter past the end). `fallbackLoop` also stops calling `meter()`, so `watch_ms` freezes after fallback.
- User-facing effect: Home-screen demo card silently turns into a looping movie after the user scrolls away and back; real buyers on mid-range Android/Low-Power-Mode iPhones lose the scroll-scrub (the product's "crown jewel") after a few janky seconds; no way back.
- Fix: Port the iOS `tick()` verbatim (gap/decay logic, `Math.max(1, …)`, `readyState > 0`), clamp in the rail handler, call `meter()` in `loopTick`, and make `player.ts` the declared canonical engine with the iOS file generated from it (see F-H-20).

### F-H-11 · P1 · `/f/%` and `/a/%` crash the Worker (uncaught `URIError`) → unbranded HTTP 500
- Where: `src/index.ts:198-202` (`decodeURIComponent(fMatch[1])` outside any try/catch). Live: `curl -I https://rendprop.com/f/%` → `500 text/plain`.
- What's wrong: `URL.pathname` preserves malformed percent-escapes; `decodeURIComponent` throws; the exception escapes `fetch()` → Cloudflare "Worker threw exception". Trivially triggerable by mangled links (e.g. a truncated share URL in SMS).
