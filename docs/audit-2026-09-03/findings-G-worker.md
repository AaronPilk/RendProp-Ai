# Findings — G · Render worker + AI pipeline (`services/worker`, `services/pipeline`, `services/marketing-video`)

## Summary
The worker (`services/worker`) and the AI pipeline (`services/pipeline`) are well-written in isolation — the
compare-and-set claim is correct, the ffmpeg output really is all-intra 60 fps with rotation baked in and no
audio (verified empirically with ffmpeg here), R2 keys line up with `uploads/index.ts`, the cost table matches
`docs/AI-COST-MODEL.md`, and the Dockerfile keeps secrets out and runs non-root. The problems are almost all at
the seams. (1) In live mode nothing ever creates a job for this worker (`ReviewSubmitView.start()` skips
`POST /renders`; `publish-app` jobs go straight to `ready`; `/ai-enhance` enqueues into an
`enhancements._requests` list that no code reads), so declutter/restage/hero cannot run — while
`publish_render` still stamps tours as "Virtually staged" from the toggles. (2) The moment the worker IS wired,
every plain job runs a paid Gemini "restage" per room because iOS sends `style:"as_is"` and the worker treats
any non-empty style as a restage request (`worker.py:192`, `enhance_bridge.py:97`). (3) HDR phone footage
(iPhone default) is only re-tagged bt709, not tone-mapped — output is washed out (measured: saturation ~20% of
reference, luma capped at 127/255); the README claims the opposite. (4) The "hard" ffmpeg timeout never fires if
ffmpeg hangs silently (verified), there is no heartbeat/reaper for orphaned `processing` jobs, and network
exceptions from `requests` bypass every `DBError` handler so a progress-PATCH blip fails a 60-minute encode.
(5) The cost-ledger policy is inverted: real provider spend fails OPEN (pipeline `CostLedger.record`) while
worker infra *estimates* fail CLOSED and kill the tour; neither uses the audited `log_job_cost` RPC; the
pipeline's shipped `.env` contains live production keys and, because of an inline-comment parsing bug, its
`MAX_GEN_COST_PER_JOB_CENTS` line is silently ignored.

## Findings (most severe first)

### F-G-01 · P0 · The worker has no producer in live mode; AI declutter/restage/hero can never run, but tours are still labelled "Virtually staged"
- Where:
  - `apps/ios/Rendprop/Screens/ReviewSubmitView.swift:340-350` (live path returns before `createRender`), `:361-369` (the only `POST /renders` call, offline/mock path only, passes a *local* asset id — see comment at `:362-364`).
  - `services/supabase/functions/renders/index.ts:98-125` (`publish-app` → `create_render_job` then immediately `publish_render` → job is `ready` in the same request; the worker's claim filter `status in (created,queued)` never sees it — `services/worker/settings.py:121`, `db.py:101-107`).
  - `services/supabase/functions/ai-enhance/index.ts:89-112` enqueues `{id, feature, image_key, frames, style, mask_key, status:"queued"}` into `render_jobs.enhancements._requests`; `services/worker/worker.py:143,192` and `services/worker/enhance_bridge.py:96-99` read only `declutter|style|hero|analyze` — `_requests`, `image_key`, `frames`, `mask_key` are never read by any code in the repo (grep confirms).
  - `services/supabase/migrations/0008_audit_round4.sql:220-222`: `v_staged := declutter or style not in (as_is…)` — derived purely from the toggles.
- What's wrong: The entire AI enhancement path (Gemini restage, Flux/Gemini declutter, Seedance hero, Claude QC, cost ledger) is unreachable from the product. `ai-enhance` returns `202 {status:"queued", request_id}` for work that will never be picked up (and, if the job was `created`, flips it to `queued` so the poller claims a job whose asset is a `renders`-bucket mp4 — see F-G-13). Meanwhile the "Design style" picker (ReviewSubmitView.swift:220-249: "Give the rooms new furniture and decor in a style you pick", badge "Included") and the declutter toggle set `enhancements`, and `publish_render` turns those toggles into `renders.staged=true`, so the public tour shows "✦ Virtually staged" + the MLS disclosure for footage that was never touched — the opposite of the compliance intent (and misleading to buyers).
- User-facing effect: Picking "Modern" or "AI declutter" does nothing visible except stamping the tour as virtually staged. No cost is incurred, no error is shown, the status screen shows "ready".
- Fix (product + code):
  1. Decide the v1 truth. Either (a) wire the worker path: `ReviewSubmitView.start()` uploads the raw capture with `role:"capture"` (already supported by `/uploads`), threads the SERVER asset id into `POST /renders` (the TODO at ReviewSubmitView.swift:362), and `RenderStatusView` polls `GET /renders/:id` until `tour` is present; or (b) remove the style picker/declutter toggle from Review & Submit until (a) ships, and keep AI edits on the photo tools only (which the copy at ReviewSubmitView.swift:203-209 already half-admits).
  2. Whichever path: `publish_render` must NOT derive `staged` from toggles alone. Add a `render_jobs.enhancement_result jsonb` (`{ran, staged, reason, spent_cents}`) that only the worker writes, and have `publish_render` use `coalesce(enhancement_result->>'staged', false)`. For app-published tours (no worker) `staged` must be false unless the on-device photo tools actually altered the tour media.
  3. Either delete `/ai-enhance` or make the worker consume `enhancements._requests` (`enhance_bridge.run_enhancement` would iterate requests, download `image_key`/`frames` from R2, apply `feature`, write results back to the request entry and to `photos`). Today it is a dead letter queue.

### F-G-02 · P0 · `style:"as_is"` triggers a paid restage on every room of every plain job
- Where: `services/worker/worker.py:192` (`if enhancements.get("declutter") or enhancements.get("style") or …`), `services/worker/enhance_bridge.py:97` (`style = enhancements.get("style") or None`), `:102`, `:105`; `services/pipeline/config.py:143-146` (`STYLES.get(style, style)` embeds unknown styles verbatim); `services/pipeline/enhance.py:71-75`; iOS always sends the raw value — `apps/ios/Rendprop/Networking/LiveAPIClient.swift:211-212,237-238` with `DesignStyle.asIs = "as_is"` (`Models/Render.swift:6`).
- What's wrong: The SQL layer treats `as_is/as-is/asis/none` as "no restage" (0008 line 222) but the worker treats any truthy string as a restage request. Verified locally: with keys present `_missing_keys(False,"as_is",False,"gemini") == []` and the pipeline would send Gemini the prompt `"Virtually restage this room in as_is style: as_is. CRITICAL, NON-NEGOTIABLE: …"` for every segment — 3.9¢ Gemini + ~0.9¢ Haiku QC (+1.7¢ Sonnet on low confidence) per attempt, up to 3 attempts per room. With no chapters (F-G-10) a 10-minute walk is 75 segments → up to ~$20 of provider spend per *plain* job, and if QC passes the render is marked `staged=True` (`worker.py:233`) and 75 "staged photos" are inserted (F-G-16).
- User-facing effect: Every Smooth render through the worker becomes an AI-mangled, "Virtually staged" tour with a ledger bill; the customer asked for neither.
- Fix: In `enhance_bridge.run_enhancement` normalise before anything else: `style = (enhancements.get("style") or "").strip().lower(); if style in ("", "as_is", "as-is", "asis", "none"): style = None; elif style not in STYLES: return EnhanceResult(ran=False, reason=f"unknown style {style!r}")` (import `STYLES` lazily from the pipeline, or duplicate the 4 names). Apply the same normalisation at `worker.py:192` (compute `wants_enhancement` once and pass it down). Also make `config.style_prompt` raise on unknown styles instead of interpolating them.

### F-G-03 · P1 · HDR phone footage is re-tagged, not tone-mapped → washed-out output; the TONEMAP_HDR path degrades SDR and fails untagged SDR (all verified with ffmpeg)
- Where: `services/worker/ffmpeg_render.py:104-121` (`_build_vf`), `:140` (`-color_primaries bt709 -color_trc bt709 -colorspace bt709` — output tags only), `:16-18` docstring; `services/worker/README.md:72,81-83` ("bt709 tags → HDR/Dolby-Vision phone footage tone-maps instead of washing out"); `settings.py:107` (`tonemap_hdr=False` default).
- What's wrong: `-color_*` output options set metadata; they do not convert. `format=yuv420p` truncates 10-bit BT.2020/PQ-HLG samples without a colour-space transform, then the stream is labelled bt709. Measured on a synthetic PQ/BT.2020 source with the worker's exact command (`signalstats`, 0–255 scale; reference SDR pattern YAVG 126 / SATAVG 114 / YMAX 214):
  - default recipe: YAVG 98.5, **YMAX 126.7, SATAVG 23.2** — the classic grey, desaturated "HDR played as SDR" look, now baked and mislabelled.
  - `TONEMAP_HDR=1` on the HDR source: SATAVG 64.9 (usable, needs curve tuning — `npl=100` + `hable` compresses even in-gamut content).
  - `TONEMAP_HDR=1` on a *bt709-tagged SDR* source: SATAVG 66.4, YMAX 139 — the chain is applied unconditionally and visibly degrades ordinary SDR footage.
  - `TONEMAP_HDR=1` on an *untagged* SDR source (common for edited/imported clips): **encode fails**, `zscale: no path between colorspaces`, rc=187 → job failed.
  iPhone 12+ record HDR (Dolby Vision 8.4 / HLG base layer) by default, so this is the majority of real uploads. The same applies to the pipeline's keyframes (`enhance.py:131-134` `extract_keyframe` → JPEG of a 10-bit HLG frame) which then feed Gemini/Claude.
- User-facing effect: Server-rendered tours look flat and grey compared with the on-device render the app promised would be "identical"; turning on the only mitigation breaks or degrades SDR uploads.
- Fix: Probe colour metadata once (`ffprobe -show_entries stream=pix_fmt,color_transfer,color_primaries,color_space`) in `probe_duration` (rename to `probe_source`). Insert the tonemap chain only when `color_transfer in (smpte2084, arib-std-b67)` or `color_primaries == bt2020`, with explicit inputs (`zscale=tin=<trc>:pin=<prim>:min=<mat>:t=linear:npl=1000` for PQ / `npl=1000` and `t=linear` for HLG, then `tonemap=hable:desat=0`, then `zscale=t=bt709:p=bt709:m=bt709:r=tv`). Keep `-color_*` tags only when the output really is bt709. Add the same conditional chain to `enhance.extract_keyframe`. Cover with a fixture test using the three synthetic sources above. Remove the false README claim.

### F-G-04 · P1 · The ffmpeg wall-clock ceiling does not fire when ffmpeg hangs silently (verified)
- Where: `services/worker/ffmpeg_render.py:163-171` (`_kill_if_overrun` is only evaluated inside `for line in proc.stdout:` at `:183-187`), `:202-211` (final bounded wait runs only after stdout closes).
- What's wrong: The overrun check is driven by progress lines. If ffmpeg blocks without emitting `-progress` output (stuck demuxer on a crafted file, blocked read, deadlocked filter), `for line in proc.stdout` blocks forever and neither the in-loop check nor the post-loop `proc.wait(timeout=…)` is reached. Reproduced with a stub that prints one progress line then sleeps: with `FFMPEG_TIMEOUT_S=3` the call was still blocked at 15 s. This defeats the "audit round 4" hardening the file comments describe (`:152-155`).
- User-facing effect: One bad upload pins a worker (and, with no heartbeat — F-G-05 — its job) indefinitely; the queue stalls.
- Fix: Start a watchdog before reading: `timer = threading.Timer(RENDER_TIMEOUT_S, _kill)` where `_kill` sets a flag and `proc.kill()`s; cancel it after `proc.wait`. Raise `RenderError("… exceeded … limit")` when the flag is set. Alternatively read stdout via `selectors` with a deadline. Apply the same to `enhance.py:121-134` (`_run`/`probe_duration`/`extract_keyframe` have no timeout at all).

### F-G-05 · P1 · No heartbeat, no lease, no stuck-job recovery; orphaned `processing` jobs are permanent and lock the org out of publishing
- Where: `services/worker/db.py:99-121` (claim sets only `started_at`), `worker.py:51-55` (SIGTERM → finish current job, which can take up to 90 min: `ffmpeg_render.py:61`), no reaper anywhere (README.md:187-189 promises "Poll stays as the fallback + reaper" — nothing implements it); `services/supabase/migrations/0008_audit_round4.sql:129-134` counts `processing` toward the 3-in-flight cap used by BOTH `POST /renders` and `publish-app`; `README.md:173` recommends Modal `timeout=1800` (30 min) while the encode ceiling is 5400 s.
- What's wrong: Any hard death (OOM, SIGKILL after the 10–30 s orchestrator grace period, Modal/Cloud Run timeout, F-G-04 hang) leaves the job at `status=processing` forever. Nothing re-queues it, the app polls a job that never finishes, and after three such orphans `create_render_job` raises `RP429` for every subsequent publish (including app-published base tours), permanently, until someone edits rows by hand.
- User-facing effect: "This workspace already has 3 renders in flight — wait for one to finish" forever; the affected renders spin at their last progress value.
- Fix: Add `render_jobs.lease_expires_at timestamptz` + `attempts int default 0` + `worker_id text` (migration). Claim sets `lease_expires_at = now()+interval '10 min'`; `_make_progress`/a background thread refreshes it every 60 s (`db.heartbeat(job_id)`). Claim filter becomes `status in (created,queued) OR (status='processing' AND lease_expires_at < now() AND attempts < 3)`; on re-claim increment `attempts`, on the 3rd failure mark `failed{type:"poison"}`. On SIGTERM, if the encode is not near completion, kill ffmpeg and PATCH the job back to `queued` (clearing `started_at`) instead of trying to finish. Exclude jobs with a stale lease from the in-flight count in `create_render_job`. Match deploy timeouts to `FFMPEG_TIMEOUT_S`.

### F-G-06 · P1 · `requests` network errors bypass every `DBError` handler — a transient PATCH failure fails a whole render; `record_cost` retries never run; `fail_job` can't mark failures
- Where: `services/worker/db.py:58-61` (`_check` only converts HTTP status codes), `:79,86,92` (`requests.get/post/patch` raise `requests.exceptions.RequestException` on connect/timeout/reset), `:128-132` (`set_progress` catches `DBError` only), `:141-147` (`fail_job`), `:173-177`, `:198-203`, `:223-236` (`record_cost` retry loop catches `DBError` only). Same class in `stream.py` (raw `requests` exceptions, though `_register_stream` catches `Exception`).
- What's wrong: Verified with an unreachable `SUPABASE_URL`: `set_progress` raises `requests.exceptions.ConnectionError` instead of logging; `record_cost` raises `ConnectionError` after 0.0 s with zero retries. Because `set_progress` is called from inside the ffmpeg progress callback (`worker.py:180`, `ffmpeg_render.py:196`), a single dropped connection to Supabase during a long encode unwinds through `render()` → `process_job` → `fail_job` (which may itself raise the same error and skip marking the job failed → orphan, F-G-05).
- User-facing effect: Renders fail (or hang in `processing`) on ordinary network blips after up to an hour of work.
- Fix: In `db.py` wrap each verb: `try: r = requests.X(...) except requests.RequestException as e: raise DBError(f"network: {e}") from e`. Keep `set_progress` advisory (already swallows `DBError`). Add the same wrapper in `stream.py` → `StreamError`. Consider a shared `requests.Session` with `urllib3.Retry(total=3, backoff_factor=0.5, status_forcelist=[502,503,504])`.

### F-G-07 · P1 · Cost ledger policy is inverted and bypasses the audited RPC: provider spend fails OPEN, infra estimates fail CLOSED and kill the tour, rollup failures duplicate rows
- Where: `services/pipeline/cost_ledger.py:93-103` (`except ProviderError: print("… continuing")` — real Gemini/fal/Anthropic spend is dropped on any ledger error), `:118-125` (non-atomic insert → separate rollup); `services/worker/db.py:208-236` (fail-closed for `feature=render`/`stream_store`, which are *estimates*, and re-`insert`s the ledger row when the *rollup* step fails at `:225-227` → duplicate rows); neither path calls `public.log_job_cost` (`migrations/0006_p0_rpcs.sql:265-300`), which is the only place the cap is enforced server-side; the pipeline cap is in-process only (`router.py:48-70`, hydrated once at `router.py:81-84`).
- What's wrong: The comment in `db.py:218-222` ("Provider spend that isn't recorded can't be capped…") justifies fail-closed, but the worker's own lines are 0.5 ¢/min compute estimates and a Stream storage estimate (recorded even when Stream is off — F-G-17), while the pipeline — the only component that actually spends money — swallows ledger failures. Net effect: a Supabase blip after a 60-minute encode fails the customer's tour for a bookkeeping line, and a Supabase blip during enhancement lets provider spend go unrecorded (exactly what the comment says must never happen). Also: `hydrate_budget` counts the worker's `render` line against the AI cap (minor), and the direct `cost_ledger` insert ignores `p_cap_cents`.
- User-facing effect: Lost tours on infra hiccups; unmetered AI spend on ledger hiccups; inflated `cost_cents` from duplicate rows.
- Fix: Route both ledgers through `log_job_cost` (PostgREST `POST /rest/v1/rpc/log_job_cost` with `p_cap_cents`) — it is atomic and enforces the cap; on `RP402` raise `BudgetExceeded`. Make `CostLedger.record` fail closed when `self.enabled` (raise `ProviderError`/`LedgerError`; the router then aborts the segment via the existing fallback-to-original path). Make the worker's infra lines best-effort (log + continue, retry later via a `pending_costs` list flushed at `finish_job`). Separate insert vs rollup retries (or drop the manual rollup — the RPC does it).

### F-G-08 · P1 · One provider/QC failure aborts the entire enhancement pass and discards already-paid results; no retry/backoff on 429/5xx
- Where: `services/pipeline/enhance.py:84-99` (`enhance_frame` catches only `BudgetExceeded`), `:203-213` (`enhance_video` loop has no per-segment `try`), `services/worker/enhance_bridge.py:136-143` (any exception → `EnhanceResult(ran=False)` — stills already written to `enh_dir` are ignored and never persisted), `services/pipeline/providers/base.py:56-83` (`request_json` — no retry on 429/5xx/timeouts), `router.py:147-160` (fallback only for restage primary).
- What's wrong: A Gemini safety refusal (`gemini.py:66-67` → `ProviderError`), a fal timeout (`fal_client.py:115`), an Anthropic 429/529 overload, a keyframe whose `-ss` is past EOF (`enhance.py:132-134` → `FileNotFoundError` at `:207`), or a judge reply whose `structure` isn't an int (`anthropic_qc.py:149` → `ValueError`) on room 7 of 8 throws away rooms 1–6 (already charged to the ledger), and the job publishes the base tour with `reason="enhancement error: …"` printed to stdout only.
- User-facing effect: Paid enhancements vanish; customer sees an un-enhanced tour with no explanation (see F-G-09).
- Fix: Wrap each segment in `try/except (ProviderError, ValueError, OSError, subprocess.CalledProcessError)` inside `enhance_video`, record `{"status":"error","reason":str(e)}` in the manifest and continue. Add bounded retries with exponential backoff in `request_json` for 429/5xx/URLError (3 attempts, honour `retry-after`). In `enhance_bridge`, if `manifest.json` exists after an exception, still harvest `status=="enhanced"` stills. Harden `_parse`/`QCResult` construction (`int(float(x))`, default on failure → verdict "regen").

### F-G-11 · P1 · `.env` inline comments make the cost cap and QC guards silently fall back to defaults (confirmed with the shipped `.env`)
- Where: `services/pipeline/config.py:22-36` (`load_env` keeps everything after `=`), `:42-53` (`_int/_float` swallow `ValueError` → default); `services/pipeline/.env.example:35-38` ships `MAX_GEN_COST_PER_JOB_CENTS=2500   # hard per-job cap …` etc.; the same loader in `services/worker/settings.py:31-59`.

Remove inline comments from the four lines in `.env.example`.
