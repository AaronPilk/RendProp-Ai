# App Review access path — Build 127 source review, 2026-10-28

**Release gate: open.** The isolated review-access branch now contains a native app-specific password sign-in path, but it is not integrated into the release build, and no funded demo account, deployed backend change, device acceptance, or App Store Connect change has been made. The production project had zero `serving_funding.source = 'app_review'` rows on 2026-10-28 (read-only count). Keep `docs/appstore/metadata/en-US/review_notes.txt` as an unsubmitted draft until the exact build and two accounts are proven; its current instruction to use the reviewer's own Apple ID does not give access to paid-equivalent features.

## Why the current route stops

Apple's [Guideline 2.1(a)](https://developer.apple.com/app-store/review/guidelines/#performance) requires full access to account-based features by an active demo account or a fully featured demo mode approved in advance. [App Review information](https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information) says demo credentials must not expire and asks for the sign-in details of single-sign-on accounts. Apple's [review instructions](https://developer.apple.com/help/app-review/before-submitting-for-review/complete-review/) also request an expired-subscription demo account when the app offers auto-renewable subscriptions. These are separate from a reviewer being able to create a new free account.

The current integration build uses only `SignInWithAppleButton` and exchanges the device's Apple identity token. Apple's [native Sign in with Apple documentation](https://developer.apple.com/documentation/signinwithapple/authenticating-users-with-sign-in-with-apple) says native apps authenticate the signed-in iCloud user. Entering a preseeded Rendprop username is not possible in that UI. A dedicated ordinary Apple Account would require the reviewer to change the device account and complete dynamic two-factor authentication; Apple [advises against sharing Apple Accounts](https://support.apple.com/guide/personal-safety/keep-your-apple-account-secure-ips7d5628cc5/1.0/1.0). Do not present that as a dependable demo credential.

The existing `app_review` sponsor cannot bridge a reviewer who signs in with their own Apple ID. `org_has_app_review_funding` requires the exact `actor_id`, owner membership, and sole-member org (`services/supabase/migrations/20261006164721_funded_serving_and_app_review_authority.sql`). The grant is limited to seven days, 500 cents total, and one lifetime issue per actor. The reviewer would create a different actor and org. A Team invitation neither transfers the actor-bound grant nor exposes the owner's private fixture library; the review entitlement allows one seat. The later Sandbox-credit migration only spends against that same actor-bound sponsor and a separately signed paid Sandbox subscription. It does not create a demo login or fund one.

## Chosen path and integration sequence

1. Add a plainly labeled **Sign in with email** option on the required account screen, with native email and secure password fields and standard accessible controls. This is an ordinary sign-in path for any existing app-specific account, including the two reviewer accounts, while the Sign in with Apple button remains. Provision the demo credentials through the operator; the form has no sign-up or password-reset action. Never ship a production username, password, token, or reviewer bypass in the app binary. Enter reviewer credentials only in App Store Connect's private App Review Information fields.
2. Exchange the credentials with Supabase Auth's password sign-in endpoint over TLS, then pass the returned session through the *same* identity, epoch, Keychain, account-switch, and saved-work adoption checks used after Apple token exchange. Do not call `/me/apple-code` for a password identity. In repository source, `handle_new_user()` creates a profile and free owner workspace for an `auth.users` insert regardless of provider; the `/me` deletion worker revokes an Apple token only when one exists, then deletes the Auth user. Verify those paths with the provisioned accounts. Supabase's [password sign-in reference](https://supabase.com/docs/reference/swift/auth-signinwithpassword) supports an existing email/password user. A read-only `GET /auth/v1/settings` on the production project on 2026-10-28 returned `external.email=true`, `disable_signup=false`, and `mailer_autoconfirm=false`, so the email provider is enabled. This does not provision or confirm either review user; use an operator-controlled Auth administration path to create confirmed users, and inspect password protection and abuse limits before activation. An Auth-issued JWT is the only backend identity accepted—no local mock or client-side review flag.
3. Provision two separate, non-anonymous, single-owner demo workspaces with fictional, rights-cleared media. One account must have repeatable access to the **actual paid feature routes** and enough unspent allowance for reviewer repetition. Prefer a genuine, renewable **Production StoreKit subscription** linked to that workspace through the existing signed transaction path; pay and keep it active through review. This uses ordinary paid funding and avoids the seven-day, one-lifetime `app_review` sponsor. If that retail path cannot be activated or maintained, a service-owned review sponsor would need a separately designed and tested sequence of non-overlapping, finance-backed renewals, including every query that currently assumes one lifetime row. Do not extend access by loosening actor/owner checks or minting an unfunded plan.
4. Give the second account a legitimately expired subscription state and confirm the exact submitted build presents and completes the entire purchase and restore flow in Apple's Sandbox review environment. Current `PurchaseDispatchAdmission` explicitly refuses an unreserved paid purchase outside ceiling mode; a known ineligible offer in ceiling mode has a separate path. The expired account, Apple introductory-offer eligibility, selected workspace, signed receipt and funding admission all need a physical-device end-to-end result. A `source='app_review'` grant does not substitute for this account.
5. Rehearse both credentials on a clean iPhone where the device iCloud account differs from the operator's. Verify sign-in, fixture access, photo edit, Listing video/Photo Motion, Aerial intro, Classic website, Restore, purchase, sign-out/account switch, and deletion. Confirm provider requests, credits, media budgets, storage and retention remain covered by real cash/limits; keep the demo fixture free of customer data. Verify an ordinary new Apple identity cannot enter either review workspace. Then replace the own-Apple-ID sentence in `review_notes.txt` with the exact tested taps, fixture label, account roles, region, build, and reachable contact. Do not put credentials in that tracked file.

If an app-specific demo login is rejected as a product choice, the alternative is a fully featured built-in demo mode with Apple's prior approval under Guideline 2.1(a). A sample website, the public limited trial, an invitation code, or a scheduled manual grant after the reviewer first signs in is not equivalent to that approved mode.

## Exact implementation gap

The isolated branch implements the review-account selection and password-session acceptance in the iOS target and exercises it with synthetic loopback identities. It must be integrated and verified in the exact submission build. No dedicated reviewer identity or paid/expired demonstration workspace has been verified. No current review Notes describe a tested login. The existing seven-day sponsor cannot guarantee access for an unknown review window, and the ordinary paid purchase path is not yet proven for a fresh expired-subscription account. This path therefore cannot be claimed in Build 127 release metadata until integration, real account provisioning and funding, Sandbox purchase testing, and a physical reviewer-device rehearsal are complete.
