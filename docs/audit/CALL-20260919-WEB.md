Scope here is `services/edge/tour-host/src/player.ts` and `services/supabase/functions/ai-photo/index.ts`; this is a component result for the main audit, not an assertion about the capture path.

## Confirmed new defects

### WEB-01 — P2: phone comparison hides the outer 44% of a landscape photograph

`src/player.ts:2895` sets the enhanced comparison to `aspect-ratio:3/4` on phones. Combined with `object-fit:cover` at line 2876, a 4:3 photo becomes a center crop, even when the slider is fully before or fully after. There is no pan/zoom action inside the comparison to reach the omitted region. This undermines the specific call requirement to compare the actual property with an edit; an edge defect can disappear from both halves of the comparison without any AI edit at all. The separate View original link remains available, so this is not deletion or loss of the source image.

Actual Chromium render at a 390×844 emulated phone viewport: the comparison is 308×410.65625 CSS pixels for a 1200×900 synthetic source. Only **56.2514% of source width is visible**. Both deliberately drawn edge-defect markers disappear. The no-JS pair retains the existing grid presentation. Synthetic screenshot inspected: `/tmp/call-web-mobile-comparison-20260919.png`.

Reproducer: `tools/audit/call-20260919/web/browser-check.mjs`, mobile geometry assertion and screenshot. The source fixture is generated in `serve-tour.mjs`; it is not customer media. Suggested correction: preserve a shared source aspect ratio, or fit both complete images into the same comparison area without clipping their outside edges. Verify landscape and portrait sources rather than replacing this with another unconditional ratio.

### WEB-02 — P2: the slider announces the opposite before/after state

`src/player.ts:1291` announces `pos + '% edited version shown'`. The real CSS at line 2878 reveals the edited image **right of** `pos`, so the visible edited proportion is `100 - pos`.

With real CDP keyboard events sent to the rendered slider:

| Key | `--p` | Announced text | Computed edited-image clip | Actual image |
|---|---:|---|---|---|
| Home | 0% | 0% edited version shown | `inset(0px 0px 0px 0%)` | Entire edited image |
| End | 100% | 100% edited version shown | `inset(0px 0px 0px 100%)` | Entire original image |

This affects both branded and unbranded pages. The current 693-assertion MLS gate does not test the meaning of this accessibility state. Suggested correction: align the value and announced description with the exposed image. Preserve div-based slider semantics and normal keyboard operation.

## Confirmed pre-existing gap, not attributed to the two waves

### WEB-03 — P2: legacy photo prompt polisher has no output denylist

`ai-photo/index.ts:639` returns `improvePrompt()` directly. Its implementation normalizes and truncates provider text at line 927 but never applies the real fair-housing denylist to that output.

The complete real handler was invoked with safe input `Brighten the room` and a stubbed provider answer `Add a family in the living room`. Both **baseline `8d32f85` and tip `7bcc624` return HTTP 200 with the prohibited text**. Applying the actual `_shared/fairhousing.ts` guard to that returned text rejects it. This is a real output-path gap, not a newly introduced regression. The subsequent `edit:custom` call still rejects the same text before charging, so this reproducer does not demonstrate generated discriminatory imagery or a bypass of that later gate.

Reproducer: `photo-offline.mjs`, `outputGap` result. The route's existing input guard and appended image-generation guardrails remain intact. A statement that this photo helper already has input **and output** denial would be inaccurate.

## Real photo-model quality test remains open

Prompt assembly does not prove that `CONDITION_LOCK` preserves cracks or that declutter/staging quality is unchanged. **No real model generation was run in this bounded subtask**, per the parent's audit boundary. Consequently the handoff's before/after image-quality acceptance gate is not satisfied.

Exact existing application route: owner-authenticated `POST /ai-photo`, body `{ "edit":"declutter" | "stage", "image_b64":..., "mime":"image/webp", "space_type":"real_estate", "style":"modern" }`. Declutter should omit masks for the prompt-only comparison. Retain the real server input guard, append the real prompt guardrails, and use the same resolved provider/model/output size for baseline and changed prompts. Do not change production prompts or router flags to perform an A/B experiment.

The local default when the router is off is Gemini `gemini-2.5-flash-image`, overridable by the deployed `GEMINI_IMAGE_MODEL`; the seeded enabled prompt-only declutter and staging routes include Gemini `gemini-3.1-flash-image`. These are **source configuration facts, not a claim that those models or routes are currently active/available in production**. Live router state, operator override, provider availability and real billed unit price were not read. No disabled route needs to be enabled. The adapter's existing `geminiImagePayload()` pins 3.x image output to 1K; use it unchanged.

The repo contains public demo inputs such as `public/assets/example-staging-before.webp` for a basic staging-quality check. That file alone is not a defect-preservation challenge set. Before a paid comparison, freeze controlled non-customer photographs with known wall/floor wear, peripheral permanent surroundings, loose clutter and a reflected photographer, and label the regions that must remain. Run the two edits with baseline and changed prompts against identical inputs; record the model, dimensions, generation attempts, timing and actual spend for every result. Inspect intended removal/furnishing quality and all marked defects, including peripheral regions at full resolution. A static SVG from the browser test cannot establish photo-edit quality.
