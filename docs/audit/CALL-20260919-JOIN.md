## J1 — P1: a short final segment makes successful cleanup delete the joined take

**Proven with real local AVFoundation and the actual caller, allocator, and cleanup.**

Locations: `apps/ios/Rendprop/Capture/CaptureView.swift:687` and `:551`; `apps/ios/Rendprop/Support/FileStore.swift:26`.

Trigger: after pausing a take, resume briefly and stop within the same wall-clock second as that final segment's creation. `FileStore.newRecordingURL()` uses a timestamp with one-second precision. `TakeJoiner` uses that same allocator for its output. Its output can therefore equal the final input URL. It removes the existing file at the output path before exporting, then `handleFinished` deletes every input after success — including the newly joined file at that shared path.

Runtime observation on synthetic inputs:

- Final segment URL allocated at `1789852114.00139`; completion at `1789852114.0126669`.
- Export returned success and the same URL as that segment.
- `joinWarning == nil`.
- Both source paths were deleted.
- The URL handed to review no longer existed.

The test copies a pre-generated 0.3-second synthetic clip into the real allocator's output path at the start of a clock second. This isolates the path alias without needing camera permission. It is not an assertion that a physical camera necessarily finalizes in 11 ms; any finish within the allocated second exposes the alias. This is newly reachable in the paused join path even though the allocator predates this wave.

Required correction: collision-resistant names for every segment and join, explicit output/input path disjointness, no pre-emptive deletion of an input alias, and validation of the complete output before destructive cleanup. Preserve source pieces until there is a durable, usable replacement.

## J2 — P1: an unreadable piece becomes silent partial success, then all original pieces are deleted

**Proven fault-injection path using actual file reads and AVFoundation, not mocked export results.**

Locations: `CaptureView.swift:668–676`, `:551`.

Trigger: one URL in a paused take becomes unreadable or cannot supply a usable video track while other pieces remain readable. The join uses `continue` for track/duration load failure and insertion failure. It can export a subset and return success; the caller then deletes all inputs, including the piece omitted from the export.

The synthetic fixture contains valid 0.3-second video, deliberately damaged MOV bytes, and valid 0.3-second video. Real `TakeJoiner.join` produces a 0.6-second output, emits no warning, and actual `handleFinished` deletes all three original files, including the damaged bytes. This proves the error handling is destructive; it does not claim the damaged fixture would independently pass CameraManager's initial duration check. A later read failure is the injected condition.

Required correction: treat any rejected piece as a failure of the whole join; retain every original byte and identify the failed piece. Never use export completion alone as proof that every segment made it into the output.

## J3 — P1: join failure leaves later footage without a recovery entry

**Failure behavior executed; missing recovery surface established by source tracing.**

Locations: `CaptureView.swift:553–559`, `:44–51`, `:592–607`; `RendpropApp.swift:1932–1943`, `:1980–1987`.

Trigger: joining fails, for example because its output cannot be created. The test provides a local ENOTDIR destination to make the real exporter fail. Both original pieces remain, but review receives only the first URL. `TakeReview` has a single URL and no collection or recovery identifier. Choosing this take stores only that first file. The local `urls` array goes out of scope after the asynchronous callback.

The warning says nothing was deleted and tells the user to record again. It offers no retry, preview/export of remaining pieces, or recovery after dismissal/relaunch. Searches of every `recordingsDir` reference and document-picker entry point found no recovery index or app UI that enumerates these unreferenced pieces. `project.yml` does not expose the app's Documents directory through file sharing. The files survive, but are not usable through the normal app workflow.

This is not a physical-device Files-app interaction test. The executable proves only-first presentation with both originals retained; the lack of app recovery is a source-level conclusion. Developer container extraction might recover files, which is not a recovery path for the nontechnical agent who just left a property.

Required correction: persist the ordered pieces with the take's tags, timing and detection metadata before joining; expose retry and per-piece export. The fallback must keep a durable reference to all pieces, not just a reassuring sentence.

## J4 — P2: another recording is allowed while joining and clears the prior take's tags

**Actual visibility predicates, disabled predicate, record action, and finish handler executed.**

Locations: `CaptureView.swift:125`, `:329–337`, `:359–360`, `:543–575`; `CameraManager.swift:538`.

`CameraManager.deliverTake` sets `.ready` before invoking `onFinish`. `handleFinished` sets `isJoining`, but `isFinalizing` checks only camera `.finalizing`. The button's disabled expression therefore evaluates false while joining. The real record action clears `tags` and invokes `startRecording`. `present` reads the shared tags only after the awaited join finishes.

Executed actor ordering: call the actual finish handler; before its unstructured Task begins, evaluate the actual button predicate and invoke its actual enabled action. `isJoining=true`, disabled=false, one start call, and the original Kitchen tag is gone when the deferred presentation runs. The CameraManager dependency is a small call-counting stub here; physical capture is not simulated. The actual joining and file cleanup remain AVFoundation.

The test proves an enabled start action and lost tags. Restarting motion logging/overwriting other metadata or recording behind the review overlay are related risks for the parent lifecycle audit, not separate hardware-proven claims in this fragment.

Required correction: joining belongs to the finalizing state from the UI's perspective. Freeze per-take metadata before awaiting work and prevent new capture/dismissal from invalidating the pending result.

## J5 — P2: detected-person ranges disappear on normal save/relaunch

**Real `PersistentStore.save` and `load` executed against a fresh temporary library.**

Locations: `Models/CaptureAsset.swift:38`; `RendpropApp.swift:1932–1943`, `:1980–1986`, `:2093–2097`.

The new `CaptureAsset.personVisibleRanges` field is assigned on Use this take, but `PersistentStore.PersistedAsset`, its save projection, restore projection, and decoder never include it. Defaulting the model field to `[]` does not add it to that separate persisted representation.

Observed: save returns true; two ranges totaling seven seconds become zero ranges and zero seconds on load. The same asset ID and file are restored, original bytes remain exact, and the existing room tag is retained. The state JSON has no `personVisibleRanges` key.

Required correction: persist and restore the ranges using tolerant decoding for older snapshots. Validate their finite, ordered, bounded times before a future billable clip extraction. This is a prerequisite for Task 2 surviving the phone-to-office/relaunch workflow.
